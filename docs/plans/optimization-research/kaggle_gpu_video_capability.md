# Kaggle 免费 GPU 作为视频能力支撑的可行性调研

> 调研日期：2026-09-23
> **状态**：📥 待调研存档 — 调研结论为 **「不作为在线视频能力后端」**，仅保留极窄的离线实验用途。保留分析记录待复查，详见 `README.md` 流转规则。
> 目的：评估能否用 Kaggle 免费算力（每周 30h GPU 配额）替代/补充本项目的视频生成能力，降低对 Agnes 免费云 API 的依赖。
> 关联：`huggingface_spaces_gpu_capability.md`（R7）— 同议题的另一免费平台调研。二者结论互补：**Kaggle 是「配额够但架构不行」，HF ZeroGPU 是「架构行但配额不行」**；横向对比见 R7 §五。
> 当前方案：视频生成 100% 依赖 Agnes 云 API（`agnes-video-v2.0`，免费），本地仅做 ffmpeg/moviepy 后处理，**全链路零 GPU 依赖**。

## 一、结论速览

| 问题 | 结论 |
|------|------|
| 能否作为本项目**在线**视频生成后端？ | ❌ **不可行**。Kaggle Notebook 无常驻进程、无公网入站端点，架构上无法承载「用户点一下就要出片」的交互式服务 |
| 免费额度够不够跑量？ | ⚠️ 名义上够（1800 min/周），但冷启动/排队/空闲断连叠加后有效利用率大幅折损，且**配额不是瓶颈，架构才是** |
| 硬件跑得动开源视频模型吗？ | ⚠️ 勉强。2026-09-15 起 P100 已停用，仅剩 **T4x2**（Turing，16GB×2，无 bf16、不支持 FlashAttention-2），现代视频 DiT 需降级改造才能跑 |
| 出片质量能否比肩现状？ | ❌ 明显倒退。T4 上可跑的是 LTX-Video / Wan2.1-1.3B 量级小模型，低于 Agnes 云端免费模型 |
| 是否值得投入实施？ | ❌ **不值得**（估算 15–25 人日，且不解决交互式服务需求） |
| 有无任何可用价值？ | ✅ 仅一处：**离线实验台**（用免费 T4 验证 prompt/模型效果，为 prompt 工程与 prompt 调优提供依据）；以及把 Kaggle Dataset 当作模型权重的分发渠道 |

**一句话**：Kaggle 提供的是「**批处理算力**」，本项目需要的是「**常驻推理服务**」，二者形态不匹配 —— 这不是配额问题，是可调度性问题。

## 二、现状盘点（读代码，不臆测）

### 2.1 项目当前视频能力构成

| 环节 | 实现 | 是否用 GPU |
|------|------|-----------|
| 视频生成（t2v / i2v / ti2vid / keyframes） | `core/api/agnes_video.py` → 云端 Agnes API | ❌（远端） |
| 视频提交限速 | `core/api/rate_limiter.py` 视频提交独立桶：**1 次/分钟/Key** | — |
| 视频轮询 | `_adaptive_poll_interval`：20s 起步，每 5 次 +5s，上限 60s | ❌ |
| 拼接 / 字幕叠加 / 音频叠加 | `core/compositor/concatenator.py`（moviepy + ffmpeg，CPU） | ❌ |
| 字幕渲染 | `core/audio/subtitle.py`（TextClip + ffmpeg overlay） | ❌ |
| 水印 | `core/compositor/watermark.py`（ffmpeg overlay，避免整片重编码） | ❌ |
| TTS | `core/audio/tts.py`（edge_tts，云端免费） | ❌ |

**关键结论**：本项目**没有任何本地 GPU 推理环节**，所有 AI 能力均为云 API（Agnes Chat / Image / Video + edge_tts）。引入 Kaggle 不是"增强现有 GPU 链路"，而是"从零新建一条生成链路"。

### 2.2 现有链路的真实瓶颈（这才是引入动机的来源）

`core/pipelines/creative/steps_video.py:159-202` 显示视频任务是**串行提交**的：

```160:202:core/pipelines/creative/steps_video.py
        # Phase 1: Submit all video tasks, saving scene state for resumability
        for scene_idx, scene_text in enumerate(scenes):
            ...
            video_id = await self.video_generator.submit_video(
                prompt=scene_text,
                reference_image_paths=[user_ref] if user_ref else [character_ref_path],
                duration=self._scene_duration(scene_idx),
                width=vw,
                height=vh,
            )
```

受视频提交桶（1 次/分钟/Key）约束，`scene_count` 默认 3、上限 30（`models/task.py:255`），即：

- 3 场景任务：提交约 3 分钟
- 10 场景任务：提交约 10 分钟
- 30 场景任务：**提交阶段就约 30 分钟**

这是本项目唯一被外部配额硬性限制的环节，也是"想用免费 GPU 自建"的真实动机。**但 Kaggle 无法解除该瓶颈**（见 §四）。

## 四、决定性硬约束（为何不能接成后端）

这一节是本次调研的核心。以下 5 条约束**单独任一条**都足以否决「在线后端」定位：

| # | 约束 | 对本项目的具体后果 |
|---|------|------------------|
| **C1** | **无常驻进程 / 无公网入站端点**。Notebook 环境不提供端口映射，无法把 FastAPI/Flask 暴露给外部调用；无 SSH，不能跑 daemon | 本项目 `web/routes/*` 的「创建任务 → 轮询进度」模型完全无法对接。用户点「开始生成」时，没有任何东西在 Kaggle 侧监听 |
| **C2** | **会话生命周期非自主**：交互式 session 空闲约 20 分钟被强制回收；关闭浏览器标签即进入回收倒计时；GPU session 上限 9h（或 12h） | 无法保证"任务提交时 GPU 在线"。用户等待期间 session 被回收 → 任务静默丢失 |
| **C3** | **环境每次重建**：pip 依赖需重装、`/kaggle/input` 只读、模型权重不缓存（除非打包成 Dataset 挂载） | 每次冷启动 5–20 分钟用于装 torch/CUDA 依赖 + 拉取数 GB 视频模型权重。**这部分也计入 30h 配额**（一旦 Accelerator 开启就计时），即配额被安装过程白白吃掉 |
| **C4** | **资源排队与不可预测**：T4x2 是共享资源池，高峰期 Accelerator 选项可能灰显/排队 | 无 SLA。项目当前「单视频 5–18s、整体超时 1800s」的时序假设全部失效 |
| **C5** | **唯一自动化路径是 `kaggle kernels push`（Commit 批处理）**：提交 → 排队 → 冷启动 → 运行 → `kaggle kernels output` 拉产物 | 这是**离线批处理**语义：一轮往返通常是「分钟级排队 + 分钟级冷启动 + 生成 + 下载」。等于把一个同步 API 调用改造成异步作业队列，且**延迟不可控** |

**C1 + C5 的组合**意味着：即便接受全部改造代价，产出的也只是一个「延迟分钟级、失败率不可控、需要用户自备 Kaggle 账号」的离线队列，**体验必然劣于当前的 Agnes 云 API**。

## 五、技术适配性：T4 跑得动开源视频模型吗？

### 5.1 硬件能力对照

| 能力 | P100（已停用） | **T4（现行）** | 现代视频 DiT 需求 |
|------|---------------|---------------|-----------------|
| 架构 / Compute Capability | Pascal / sm_60 | Turing / sm_75 | 多数项目要求 ≥ sm_80 |
| Tensor Core | ❌ 无 | ✅ FP16 TC（~65 TFLOPS FP16） | 依赖 |
| bfloat16 | ❌ 不支持 | ❌ 不支持 | **绝大多数 2025+ 视频模型默认 bf16** |
| FlashAttention-2 | ❌ | ❌（需 sm_80+） | Wan2.1 / HunyuanVideo / LTX-Video 默认启用 |
| FP8 | ❌ | ❌ | 加速常用，非必需 |
| 单卡显存 | 16GB | 16GB | 720p 5s：量化后 8–16GB 起 |
| 卡间互联 | PCIe | PCIe（T4x2 走 PCIe，无 NVLink） | 单样本扩散推理**无法有效多卡切分** |

### 5.2 实际后果

- **P100 已停用这一变化极为关键**：Pascal 无 Tensor Core、无 bf16、无 FA2，在 2026 年已是"跑现代视频模型基本不可用"的状态。它的退役反而说明免费池在向可用方向收敛，但收敛终点（T4）**仍低于**主流视频模型的实际门槛。
- **T4x2 的"双卡"是营销上的安慰**：扩散模型单次采样（batch=1）无法跨卡切分，实际只能用单卡 16GB。除非把「多个场景片段」按卡分发 —— 但那样每卡仍受 16GB + 无 bf16 限制。
- **可跑量级**（保守估计，需实测）：LTX-Video 2B / Wan2.1-T2V-1.3B / SVD 一类小模型，fp16 + attention 降级（xformers 或 SDPA），512–768p、5s 片段预计 **2–6 分钟/段**（对比 RTX 4090 约 10–30 秒/段，T4 慢 5–10 倍）。
- **质量对比**：这些开源小模型的出片质量明显**低于** Agnes `agnes-video-v2.0`。也就是说，自建在"质量"维度同样是**倒退**，换来的是一个仍然受限的批处理链路。

> 注：未经实测，§5.2 的时间估算为数量级判断。若后续确需结论，应做一次最小验证（Kaggle 上跑 LTX-Video 单段 5s，记录耗时与显存峰值）。

## 六、量化测算：30h/周到底能干多少活

| 项 | 数值 |
|---|------|
| 理论额度 | 30 h/周 = 1800 min/周 ≈ 257 min/天 |
| 每次 session 冷启动成本 | 5–20 min（装依赖 + 拉权重，**计入配额**） |
| 有效算力利用率（含排队、排队后闲置、输出下载） | 乐观 60–70% → **约 1100–1250 min/周** |
| 按 3 min/5s 片段 | 约 **370–420 段/周** ≈ 53–60 段/天 |
| 本项目需求侧（假设） | 10 任务/天 × 3–10 场景 = **30–100 段/天** |

**结论**：名义配额与需求在一个数量级内，甚至偏紧。但**这不是能不能跑量的问题** —— 即便配额翻倍，C1/C5 的架构错配依然存在。配额从来不是本项目引入 Kaggle 的可行性瓶颈。

## 九、预判效果与代价

### 9.1 若强行实施（引用 `README.md` 要求的四要素）

1. **现状盘点**：项目视频生成为云端 API，本地零 GPU；唯一瓶颈是视频提交桶 1 次/分钟/Key。
2. **真实增量**：**接近零甚至是负的**。不解除提交限速瓶颈（仍受 Kaggle 排队与 session 限制）；出片质量下降；增加用户侧配置负担。
3. **代价**：新增 Kaggle 凭据管理、notebook 模板与版本维护、模型权重 Dataset 管理、任务编排从"提交-轮询"重写为"打包-推送-排队-拉取-校验"、6 条流水线视频生成步骤的回归面全覆盖；估算 **15–25 人日**，且需长期维护以应对平台策略变更。
4. **硬限制**：C1–C5（§四）+ T4 硬件天花板（§五）。

### 9.2 成本收益判断

**代价 ≫ 收益**，且收益方向错误：用户想要的是"更快的出片"，Kaggle 给的是"更慢且更差的出片"。

## 十、结论与建议

### 10.1 主结论

**❌ 不作为本项目的视频能力支撑方案。**

不匹配的根因不是配额（30h/周在数量级上够用），而是**平台形态**：Kaggle 是「交互式 notebook + 离线批处理」平台，本项目需要「常驻推理服务」。二者之间不存在低成本的桥接方式。

### 10.2 唯一保留的有限用途

| 用途 | 说明 | 优先级 |
|------|------|--------|
| **离线 Prompt/模型实验台** | 用免费 T4 跑 LTX-Video / Wan2.1-1.3B，横向验证 prompt 表达方式与镜头语言对出片的影响，为 `core/screenwriter/` 的 prompt 工程提供**实证依据**（当前 prompt 策略缺乏可量化验证手段） | P2（有需求时再做，写独立实验脚本，不进入主仓依赖） |
| 模型权重托管 | Kaggle Dataset 作为公开模型权重的分发渠道 | P3（无必要） |

> 注意：上述用途**不引入任何仓库代码依赖**，纯人工/脚本级实验，与主线解耦。若要做，应新建独立实验目录而非改动 `core/`。

### 10.3 若未来确需自建视频能力，建议路线

优先 **Modal（免费额度内 serverless GPU，具备 HTTP 常驻端点）**，并复用 v7.0 已建立的 Provider 抽象模式把它做成**可选的视频 Provider**（与文本 Provider 同构：`provider` / `base_url` / `api_key` / `models[]`）；本地消费级 GPU 分支作为离线部署选项。**Kaggle 不在候选序列内。**

## 十一、未实施原因与复查触发条件

**未实施原因**：架构形态不匹配（无常驻服务/无公网入站/非自主生命周期），且硬件天花板（T4、无 bf16、无 FA2）叠加导致出片质量与速度双降；实施代价 15–25 人日，收益为负。结论为"不值得做"，故按 `README.md` 流转规则**保留分析记录，不删除**。

**复查触发条件**（满足任一即重开评估）：

1. Agnes 免费视频 API 转为收费、下线或大幅限流（**最高优先级**，这是项目"完全免费"卖点的单点依赖）；
2. Kaggle 官方开放常驻服务 / 公网端点 / 长时间服务器型实例；
3. Kaggle 免费池引入 **L4（sm_89，支持 bf16 + FA2）或更高** 且确认对所有用户开放（可消除 §五 的硬件天花板）；
4. 项目定位从「在线 Web 服务」转向「离线批量出片工具」——届时批处理语义反而匹配；
5. 出现可直接复刻的"同类项目用 Kaggle 承载视频生成"的成功案例（需验证其延迟与失败率）。
