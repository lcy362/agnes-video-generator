# Hugging Face Spaces 免费算力作为视频能力支撑的可行性调研

> 调研日期：2026-09-23
> **状态**：📥 待调研存档 — 调研结论为 **「作为在线视频生成主链路不可行（免费配额仅 5 分钟/天）」**；架构形态是本轮唯一真正成立的免费方案，但被配额否掉。仅保留一个待验证的窄方向：**ZeroGPU 作为轻量视频增强（口型/超分/插帧）可选插件**。
> 关联：`kaggle_gpu_video_capability.md`（R6）— 两份调研同属「免费云 GPU 能否支撑本项目视频能力」议题，结论互为补充（见 §五 横向对比）。
> 目的：承接 R6，评估 Hugging Face Spaces（ZeroGPU）能否作为视频能力后端。
> 当前方案：视频生成 100% 依赖 Agnes 云 API（免费），本地仅 ffmpeg/moviepy 后处理，**全链路零 GPU 依赖**。

## 一、结论速览

| 问题 | 结论 |
|------|------|
| 架构上能否接成本项目后端？ | ✅ **能**。Space 是持久 Web 应用，提供公网 HTTPS 端点（`gradio_client` 或 HTTP API），这是 R6 中 Kaggle 完全缺失的能力 |
| 硬件够不够？ | ✅ **远超 Kaggle**。`large` = 半块 **RTX Pro 6000 Blackwell，48GB**；`xlarge` = 整块 96GB。支持 bf16 / flash-attention 3（T4 均不支持） |
| 免费配额够不够？ | ❌ **致命短板：免费账户 5 分钟 GPU/天**（≈ Kaggle 30h/周的 1/50）。一天只够出约 10 段 5s 视频 |
| 单次调用限制？ | ⚠️ 默认 **60 秒**，`duration` 可延长（官方示例 120 秒）。大视频模型单段采样可能超限，而**扩散采样不可切段** |
| 出片质量能否比肩现状？ | ❌ 仍倒退。为在 120 秒内出片，只能用 LTX-Video / Wan2.1-1.3B 量级小模型，低于 Agnes 云端免费模型 |
| 是否值得实施？ | ❌ **作为生成主链路不值得**。仅「轻量视频增强插件」方向值得保留待验证（P3） |
| 一句话 | **R6 是「配额够但架构不行」，本轮是「架构行但配额不行」—— 两条路都堵，但堵点不同。** |

## 二、现状盘点（与 R6 共享，此处只列差异结论）

本项目视频生成链路无本地 GPU 环节，唯一被外部配额硬约束的是**视频提交桶 1 次/分钟/Key**（`core/api/rate_limiter.py`，串行提交见 `core/pipelines/creative/steps_video.py:159-202`）。

ZeroGPU 对本项目的意义需澄清一点：**它不可能缓解提交限速**（ZeroGPU 是同步调用，反而是"排队 + 单次 60s 上限"的新约束），它只能作为**生成源的替换**。

## 三、ZeroGPU 事实核查（官方原文）

### 3.1 每日 GPU 配额（最关键）

| 账户类型 | 每日含 GPU 配额 | 队列优先级 |
|---------|---------------|-----------|
| 未登录 | **2 分钟** | 低 |
| **免费账户** | **5 分钟** | 中 |
| PRO（$9/月） | 40 分钟（可用 credits 扩展） | 最高 |
| Team 组织成员 | 40 分钟（可扩展） | 最高 |
| Enterprise 组织成员 | 60 分钟（可扩展） | 最高 |

- 配额自**首次使用 GPU 起满 24 小时**重置（非自然日）。
- **剩余配额直接影响排队优先级** —— 配额越低，越排在后面，形成正反馈恶化。
- 超额：PRO/Team/Enterprise 可按 **$1 / 10 分钟**从 credit 扣费；免费账户无此通道，用完即等重置。

### 3.2 调用形态与硬件

| 项 | 规格 |
|---|------|
| 单次 GPU 运行上限 | **默认 60 秒**；`@spaces.GPU(duration=120)` 可延长；支持按入参动态计算时长 |
| 调度特性 | 声明时长越短，**排队优先级越高**（官方建议短函数设短时长） |
| GPU `large`（默认） | **半块 RTX Pro 6000 Blackwell，48GB 显存**，配额 **1×** |
| GPU `xlarge` | **整块 RTX Pro 6000 Blackwell，96GB 显存**，配额 **2×**（例：45 秒有效任务 = 90 秒配额），排队更久 |
| 并发 | 共享基础设施，支持单应用并发多 GPU；具体并发上限文档未给出 |

### 3.3 平台能力限制

| 限制 | 内容 | 对本项目的含义 |
|------|------|--------------|
| **SDK** | **仅兼容 Gradio SDK** | 必须写 Gradio app，不能直接跑 FastAPI；本项目需新增一层 Gradio 适配 |
| PyTorch | 2.8.0 → 最新（列出 2.8.0/2.9.1/2.10.0/2.11.0/2.12.1/2.13.0） | 版本窗口较新，老代码可能需适配 |
| Python | 3.12.12 / 3.10.13 | 与项目 3.10+ 要求兼容 |
| `torch.compile` | **不支持** | 只能用 AOTI（提前编译，需 torch 2.8+） |
| 模型加载 | 必须在**根模块级 `.to('cuda')`**，禁止在 `@spaces.GPU` 内懒加载 | 影响显存占用与冷启动行为 |
| 优化建议 | 官方推荐 **AOTI + flash-attention 3** | flash-attn 3 可用（T4 完全不可用） |
| 休眠策略 | **ZeroGPU 文档未覆盖**；已知 `cpu-basic` 免费层 48h 无访问休眠，升级硬件默认不休眠 | ⚠️ 需实测确认 ZeroGPU Space 是否长期保活 |

### 3.4 托管自己 Space 的数量上限

| 账户类型 | ZeroGPU Space 上限 | 前置条件 |
|---------|-------------------|---------|
| **免费个人账户** | **2 个** | 邮箱已验证 + **账号注册满 30 天** |
| PRO 个人账户 | 10 个 | — |
| Team / Enterprise 组织 | 50 个 | 可对全部组织成员启用 |

> 注：Gradio / Docker Space 的**创建**权限在 2026 年已收紧为需付费计划（PRO / Team / Enterprise），免费个人账号的例外通道正是「最多 2 个 ZeroGPU Gradio Space」。即：**ZeroGPU 是免费用户当前唯一能自建 GPU 服务的路径**，但上限 2 个、且需账号满 30 天。

### 3.5 一个相对优势：冷启动不吃配额

ZeroGPU 设计为「**函数外走 PyTorch CUDA 模拟模式，装饰器内才用真 GPU**」。因此模型在根模块级加载/搬到 CUDA 的过程**不占用 GPU 配额**（时间成本仍在，但不计费）。

**对比 R6**：Kaggle 只要 Accelerator ≠ None 就全程计时（装依赖、拉权重、发呆都算），30h/周被大量浪费。这是 ZeroGPU 相对 Kaggle 少有的结构性优势。

## 四、量化测算：5 分钟/天到底能出多少片

| 项 | 数值 |
|---|------|
| 免费账户日配额 | 5 min = **300 GPU 秒/天** |
| 单段 5s 视频实测预估（Blackwell 48GB） | LTX-Video 2B ≈ 15–40 s；Wan2.1-T2V-1.3B ≈ 30–60 s；更大模型（Wan2.1-14B / HunyuanVideo）**> 120 s，无法在单次调用内完成** |
| 折合产出 | **约 8–20 段 5s 视频/天**（理论上限，不含失败与重试） |
| 本机项目典型任务 | 3 场景任务 = 3 段（`scene_count` 默认 3）；10 场景任务 = 10 段 |
| 结论 | **3 场景任务 ≈ 3 个/天封顶；10 场景任务一天就把配额吃光**；`scene_count` 上限 30 的场景（`models/task.py:255`）**单任务即超日配额，必然失败** |

### 4.1 最容易被忽略的陷阱：配额属于「部署者」，不是「用户」

| 部署模式 | 后果 |
|---------|------|
| 项目作者部署一个公共 Space 供全体用户使用 | 5 分钟/天被所有用户瓜分 → **第 2 个用户的任务就会因配额耗尽失败**。等于把免费额度变成一个不可用的共享资源 |
| 每个用户自建自己的 Space | 用户需：HF 账号 **满 30 天** → 验证邮箱 → fork/上传代码 → 部署 Gradio app（含模型选择与 requirements 配置）。**门槛不低于 Kaggle，而配额只有其 1/50** |

无论哪种模式，**免费层都无法支撑多人使用的在线服务**。

### 4.2 与 R6 的配额对比

| 平台 | 名义配额 | 折算每天 | 相对 |
|------|---------|---------|------|
| Kaggle 免费 | 30 h / 周 | ≈ 257 min/天 | 1×（基准） |
| **HF ZeroGPU 免费** | 5 min / 天 | **5 min/天** | **≈ 1/50** |
| HF ZeroGPU PRO（$9/月） | 40 min / 天 | 40 min/天 | ≈ 1/6.4（且已非免费） |

Kaggle 的配额之所以"看起来多"，正是因为它把**冷启动、装依赖、发呆全部计费**且效率极低；ZeroGPU 效率高但额度极小。两者最终都落在"不够支撑生产服务"这一点上。

## 五、横向对比：三条免费路径

| 维度 | 现状（Agnes 云 API） | Kaggle 免费（R6） | **HF ZeroGPU 免费（本轮）** |
|------|---------------------|------------------|---------------------------|
| 常驻服务 | ✅（远端） | ❌ | ✅ **Space 持久在线** |
| 公网端点 | ✅ | ❌ | ✅ **HTTPS + gradio_client** |
| 协议形态 | 原生 REST（提交 + 轮询） | 离线批处理（kernels push） | **同步调用，单次 ≤60s/120s** |
| 名义配额 | 提交 1 次/分钟/Key | 30 h/周（≈257 min/天） | **5 min/天** |
| 硬件 | 云端 `agnes-video-v2.0` | T4×2（无 bf16 / 无 FA2） | **RTX Pro 6000 Blackwell 48GB（bf16 + FA3）** |
| 出片质量 | 基准 | 下降 | 下降（受 120s 时限） |
| 冷启动计费 | — | 全部计费（浪费大） | **不计配额** |
| 用户门槛 | 仅 Agnes Key | 手机验证 + notebook 管理 | HF 账号满 30 天 + 自建 Gradio Space |
| 框架限制 | 无 | 无（任意 pip） | **仅 Gradio SDK + PyTorch 2.8+；无 torch.compile** |
| 结论 | 🏆 现状最优 | ❌ 不可行 | ❌ 不可行（作为生成主链路） |

**核心判断**：ZeroGPU 在「架构」维度是本项目见过的最优免费方案（持久 + 公网 + Blackwell），但「配额」维度是全场景最差（5 分钟/天）。**5 分钟/天的额度决定它只能做 demo，不能做服务。**

## 六、附带路径评估：调用他人的公开视频生成 Space

技术上是免费的捷径：任何公开 Space 都能当 API 用（`gradio_client` 或 HTTP），无需自建、不占自己配额、硬件也好。官方 `gradio-client` 文档明确说明：

> While you can use any public Space as an API, you may get rate limited by Hugging Face if you make too many requests.

| 风险 | 说明 |
|------|------|
| 限流 | HF 对高频调用第三方公开 Space 会限流；排队不可控 |
| 消耗他人配额 | 实际占用的是 Space 所有者的 ZeroGPU 配额与转让成本 —— 高频调用等于**耗损社区个人的免费额度**，与开源项目的公共属性相冲突 |
| 零 SLA | Space 随时可能被作者删除/私有化/改版/停机，且模型结构变更即调用签名失效 |
| 许可证 | 模型许可证各异（部分禁商用、部分要求署名）；生成内容权利归属需逐个核查 |
| 隐私 | 用户 prompt / 参考图会发送至第三方个人 Space，与"数据不出本机"的部署预期冲突 |

**结论**：技术上"能跑通"，但产品化不可接受 —— 把用户的免费额度消耗转嫁给社区个人的 demo Space，是对第三方资源的滥用，且随时断裂。**明确不做。**

## 七、唯一保留的窄方向：ZeroGPU 作为「轻量视频增强」可选插件

这是本轮调研中**配额与需求唯一匹配**的用法。因为增强类任务单次耗时刻度是 **5–20 GPU 秒**，而非生成类的 30–120 秒：

| 候选能力 | 单次 GPU 耗时（估） | 300 秒/天可处理 | 是否填补现状空白 |
|---------|------------------|---------------|----------------|
| 口型同步（LatentSync / Wav2Lip 量级） | 5–20 s / 5s 视频 | 15–60 次 | ✅ 正好对应 R1 存档中「对话支持口型缺口大」的空白 |
| 视频超分（Real-ESRGAN 量级） | 5–15 s / 5s 片段 | 20–60 次 | ✅ 云端 API 不提供 |
| 视频插帧（RIFE / FILM 量级） | 3–10 s / 5s 片段 | 30–100 次 | ✅ 云端 API 不提供 |

**为何仍只给 P3、且不建议现在做**：

1. **需要用户自建 Space**（HF 账号满 30 天 + 部署 Gradio app），把"一键部署"退化为"先学 HF"；
2. **视频须上传到 Space**：传输耗时、请求体大小限制、隐私面扩大（与本地处理定位冲突）；
3. **单次 60/120 秒限制**要求长视频切段处理，误差与拼接复杂度上升；
4. 需先有**真实需求**（例如用户明确要求口型同步），否则是"有能力无场景"。

> 若未来要做，应作为**可选的增强 Provider 插件**（与 v7.0 文本 Provider 同构：用户自行提供 base_url / token），且**默认关闭**，不能进入主链路依赖。

## 八、若未来确需自建视频能力（承接 R6 结论）

| 方案 | 常驻 | 配额/成本 | 可跑模型 | 评价 |

## 九、预判效果与代价（对照 `README.md` 四要素）

1. **现状盘点**：视频生成为云端 API，本地零 GPU；`rate_limiter` 视频提交桶 1 次/分钟/Key 是唯一硬约束。
2. **真实增量**：作为生成源 → **负增量**（5 分钟/天配额、60s 单次上限、质量下降、用户需自建 Space）。作为增强插件 → 有真实增量（口型/超分/插帧），但门槛与工程量不小。
3. **代价**：若做生成主链路，需新增 Gradio Space 代码库（独立于主仓维护）、HF 凭据与部署文档、把"提交-轮询"改为"同步调用 + 排队重试"、6 条流水线视频生成回归面全覆盖；**且因配额必然失败**。若做增强插件，需新增视频上传通道、切段处理、可选 Provider 抽象，估算 **8–12 人日**。
4. **硬限制**：§三（配额 5 分钟/天、60s 单次、仅 Gradio SDK、2 个 Space、账号满 30 天）+ §四（配额归属部署者）。

## 十、结论与建议

### 10.1 主结论

**❌ 免费 Space 不能作为本项目的视频生成能力支撑。**

理由层级清晰：
1. **架构问题已解决**（持久服务 + 公网端点 + Blackwell 48GB），比 Kaggle 优；
2. **但配额 5 分钟/天是硬墙**，比 Kaggle 差 50 倍，且归属于部署者账号，多人共享即失效；
3. **单次 60s/120s 上限**进一步锁死可跑模型规模（只能小模型 → 质量低于现状）；
4. **仅 Gradio SDK** 增加适配成本，与项目 FastAPI 架构异质。

### 10.2 建议

| 建议 | 优先级 |
|------|--------|
| 维持 Agnes 云 API 为视频生成主链路，不做改动 | — |
| 不引入 HF Space 作为生成后端 | — |
| 不调用第三方公开视频 Space（§六） | — |
| 把「ZeroGPU 作为轻量视频增强可选插件（口型/超分/插帧）」记入待验证清单 | P3（先有真实需求） |
| 若确需自建生成能力：Modal（可复用 v7.0 Provider 抽象）> 本地 GPU > HF PRO > Kaggle | — |

## 十一、未实施原因与复查触发条件

**未实施原因**：免费配额 5 分钟 GPU/天，仅够约 10 段 5s 视频，且配额归属 Space 部署者账号，多人使用立即失效；单次 60s/120s 上限强制降级到小模型，出片质量低于现状。结论为"不值得做"，按 `README.md` 流转规则**保留分析记录，不删除**。

**复查触发条件**（满足任一即重开评估）：

1. **HF 提高免费配额**至 ≥30 分钟/天（届时架构优势会立刻兑现，"架构行 + 配额行"成为唯一同时满足两条的免费方案）；
2. Kaggle 线路的任何触发条件（见 R6 §十一）成立，需要一个替代免费算力平台；
3. HF 开放 **FastAPI / Docker SDK 使用 ZeroGPU**（消除 Gradio 异质适配成本）；
4. 用户群体出现明确的**口型同步 / 超分 / 插帧**需求（激活 §七 的 P3 方向）；
5. ZeroGPU `duration` 上限提升或支持长任务排队（使大模型单次出片成为可能）。
