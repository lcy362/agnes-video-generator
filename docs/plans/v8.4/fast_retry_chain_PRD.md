# v8.4 快速重试自动接力（两轮间隔 X）PRD

> 状态：🟢 已实施
> 关联：`docs/plans/v7.7/fast_retry_PRD.md`（快速重试）、`docs/plans/v8.0/fast_retry_auto_PRD.md`（自动模式）、`docs/plans/v8.3/long_task_mode_PRD.md`（长任务模式）
> 用户诉求（2026-11-19）：
> 「改成常规节奏重试 X 分钟后，自动再开一轮快速重试，快速重试开关新增配套参数：两轮快速重试间隔（分钟），即 X。」

---

## 一、问题

快速重试一轮固定 `y` 分钟（默认 3）。到期后回到常规忙轨，如果上游队列还没空出来，
用户只能盯着进度页反复手动点开关——尤其在长任务模式下要等几十分钟时体验很差。

## 二、方案

快速重试配置新增 **两轮间隔 X（分钟，默认 5，1–60）**：

1. 一轮到期 → 进入「接力等待」（`chain_pending=true`，记录到期时刻 `chain_started_at`）；
2. 常规忙轨照常按既有节奏重试（首跳 0s，之后 30–60s）；
3. 距到期满 X 分钟后的**下一个忙信号**处，自动开新一轮，参数沿用本任务当前值
   （`per_minute` / `minutes` / `X`），`rounds += 1`；
4. 终止条件：提交成功（`on_success` 清接力）、用户手动关闭（`chain_pending=false`）、
   长任务预算耗尽（`allow_extend` 返回 False → 抛队列满）。

## 三、语义边界

| 项 | 约定 |
|---|---|
| 计时起点 | 上一轮**到期时刻**（不是上一跳请求时刻） |
| 计时口径 | 墙钟（提交重试循环里没有渲染/合成，墙钟 ≈ 等待时间） |
| 判定时机 | 下一次忙信号处，因此实际误差 ≤ 一个常规间隔（30–60s） |
| 与全局 auto 的关系 | auto 负责「第一次自动开」；接力负责「到期后再开」。两者独立，手动开的也能接力 |
| 与长任务模式的关系 | 接力期间照常累计忙轨等待，占用长任务预算；预算耗尽后不再接力 |
| 续传 | 清 `chain_pending` / `chain_started_at` / `rounds`，其余参数保留 |

## 四、配置

- 任务级：`POST /api/tasks/{id}/fast-retry` 新增 `interval_minutes`（0 = 保留当前值，1–60，越界 422）。
- 全局：`POST /api/config/fast-retry` 新增 `interval_minutes`；`GET /api/config.fast_retry` 下发。
- 前端：进度页「快速重试」参数区与设置页「04 快速重试」参数区各新增一个输入框。

## 五、验收

| 编号 | 场景 | 预期 |
|---|---|---|
| FC1 | 到期后未满 X | 保持关闭，常规节奏重试，`rounds` 不变 |
| FC2 | 满 X 分钟 | 自动开新一轮，`rounds+1`，参数沿用，消息 `progress.video.fast_retry.chain` |
| FC3 | 连续多轮 | 每轮到期都能接力，`rounds` 递增 |
| FC4 | 用户手动关闭 | 清接力状态，不再自动开 |
| FC5 | 中途提交成功 | 清 `available` 与接力状态，任务结束 |
| FC6 | 与长任务模式同开 | 接力期间预算照常消耗，耗尽后抛队列满 |
| FC7 | 续传 | 接力状态清零，参数保留 |
